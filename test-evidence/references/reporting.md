# 测试报告填写

## 先读模板

1. 用 `office-docx` 读取模板的块结构、样式、表格和页眉页脚；保留原有样式和图表占位。
2. 先确定每个章节/表格的目标内容，再一次性替换，避免反复覆盖导致格式漂移。
3. 模板中的示例数字、旧项目名称和旧结论必须全部替换；不要留下模板痕迹。

## 建议结构

- 引言：目的、范围、被测系统与版本。
- 参考文档：用例、模板、手册、计划、功能清单、规范。
- 测试设计：方法、范围、重点场景、环境与账号。
- 测试执行：执行轮次、范围、覆盖表。
- 缺陷统计：按版本/模块分布、级别、观察项。
- 测试建议：修复优先级、回归范围、监控建议。
- 结论：通过/有条件通过/不通过，并说明条件。
- 变更记录：版本、日期、变更描述、作者。

## 覆盖表

至少包含：模块、用例总数、通过数、失败/阻塞/未执行、是否通过。数字来源必须是矩阵和证据 JSON，不能手填估算。

一致性规则：

- `总数 = 通过 + 失败 + 阻塞 + 未执行`。
- 文字描述的“未执行场景”数量与表格行一致；如果按场景组统计，要写明口径。
- BUG 清单条数 = 报告缺陷条数；观察项单独说明，不混入缺陷数。
- 结论与最高级别缺陷一致：存在严重缺陷时不能写“无条件通过”。
- 每个失败用例都能在 BUG 清单或证据索引中找到对应项。

## 证据索引

建议表格：证据类型、文件/位置、时间点、证明内容。视频时间点使用成片时间；原始录屏单独列出，不混用。

## DOCX 操作

- 使用 `office-docx` 的 `read_context` → `apply_ops`/`replace_blocks` → `check_document` → `save_document` 流程。
- 表格内容优先整体替换，保留表头和样式；大表分段提交。
- 设置 `pageBreakBefore` 避免表格标题与内容分页断裂。
- 保存后转 PDF 抽查页数、表格是否跨页、中文是否缺字；结构检查不能代替目视检查。

## 结论措辞

- **通过**：范围内用例全部通过，或无阻断性缺陷。
- **有条件通过**：主流程可用，但存在需修复/确认的缺陷或未执行场景；写明条件和后续回归范围。
- **不通过**：存在阻塞或严重缺陷，主流程/合规要求无法满足。

不要用“基本通过”“应该没问题”等无法审计的措辞。
